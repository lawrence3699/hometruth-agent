# 租房 Agent：黑客松方案

整理日期：2026-10-24（悉尼）。截止：2026-10-27 23:45 UTC，即 10-28 周三 10:45 AEDT。
依据：10-23 晚团队会议录音（两份转写互相核对）、赛事官方规则（10-22 核实）。

## 1. 目标总结

做什么：一个替租客"核对房子"的 Agent。用户用大白话说想要怎样的生活（预算、通勤、做饭、阳光、家具、空调……），Agent 把每套候选房按这些条件逐条核对，给出三种答案：确定满足、推断满足或不满足、没人知道。没人知道的，自动变成下一步：问中介、看房时看、或签约时核；中介回复、自己看房拍的照片进来后，结论和排名跟着更新。

给谁用：悉尼学生、异地租客、没法频繁实地看房的人。

一句话卖点：get rid of filters，用自然语言筛任何你真正在意的东西。

我们新增的贡献（不求没人做过，只求差异清楚）：
- 把生活语言变成房间级、时间级的检查项，而不是地段、价格、几房几卫这几个固定 filter。
- 把散在挂牌、照片、公开数据、中介回复、自己看房所见里的证据拼成一张带状态和出处的核对表，分清"知道、推断、不知道"，不替用户猜。
- 把"不知道"变成最值得问中介的问题，新证据到了再更新，并保留变化记录。

黑客松目标：10-28 前交出可运行的演示、1 到 4 分钟视频、幻灯片、GitHub 仓库和 README，以及 Zetaris、Meterless、Cursor、NVIDIA 的使用说明；主报 Track 1。

## 2. 会议共识

- 三个主赛道都是工程向（分散信息整合、可解释、推理架构），Wildcard 自由选题。黑客松要脱颖而出得有趣、贴近生活，平台 channel 里的 idea 大多像 AI 生成的，做得差不多就埋没了。
- 租房方向被接受的理由：数据多、很现实、能卖给 REA 和 Domain；现有网站的 filter 只有固定几项，真正看房在意的东西（装修风格、新旧、采光、噪音、家具、空调、厨房、洗衣）搜不到。
- 和直接问 GPT 的区别：GPT 只能看广告文字，广告现在还专门写给 GPT 看；我们"先射箭再画靶"，手里有广告没有的数据（朝向、遮挡、隔音这些公开可算的，加上中介书面回复和租客自己看房看到的）。
- 数据不爬网站（合法性存疑，周末来不及要授权），按 REA 和 Domain 的字段结构自己造合成数据，维度从一份真实的代看房记录样本（docs/reference）提炼；隔音这类数据当作有。
- 视频谁剪得好用谁的，避免 AI 味。

## 3. 产品定义

- 名字（暂定）：HomeTruth，中文"看房核对员"。
- 输入：大白话需求（可附参考图）；材料分五段（第 6.1 节）：挂牌就有的（挂牌页、照片、户型图）、公开可查可算的（租金统计、通勤时间、太阳几何、建筑高度）、问中介能拿到的（中介回复、by-laws、法定披露）、自己看房看到的（按清单拍的照片和勾选）、签约时才拿到的（租约草案、条件报告、inventory，只做最后核对）。
- 输出：每套房一张核对表，条件 × 状态（满足、不满足、有冲突、未知）× 证据出处；每个未知项的下一步（问中介 / 看房时看 / 签约时核），其中最值得问中介的 3 个问题单列；跨房源比较；新材料进来后的变化记录。
- 范围：首版不做三维重建和虚拟试住。"冬天下午客厅有没有太阳"这类问题由朝向、楼层、前方遮挡字段推断，标"推断"。
- 偏好规则包（可选）：用户说出"我在意风水"这类文化偏好时，才把对应规则包装进检查清单。默认关闭，不打总分，每条和其他维度一样单独给状态和出处。首版只做风水包，且只做能从户型图和挂牌地址核对的几条（见附录规则 R-H 段）。产品不判断风水好坏，只核对用户在意的布局事实；凶宅属于法定披露事实，不在这个包里。

判断规则（按"材料能证明什么"定，依据见附录《01_判断规则与证据分级.md》）：
- 挂牌 features 是房产级勾选，"有空调"推不出"卧室有空调"；文案是营销，"sun-drenched"、"minutes to" 只算线索。
- 照片里的家具不算随租：有 Virtual Staging 水印的视为不存在，没水印的也可能是上个租客或业主的；家具以 inventory 或合同包含项为准。
- 平面玻璃炉灶分不出陶瓷炉和电磁炉；没拍到的房间是未知，不是"没问题"。
- 户型图有指北针才能定朝向；日照还要单元位置、楼层、邻楼遮挡，所以最多到"推断"。
- 条件报告在签约前或签约时才拿到，是签约前的最后核对，不是筛选输入；它只记 Y/N，不记几台、性能、插座数量、窗帘类型。
- 霉菌和虫害在条件报告上有专门 Y/N：有表填 No 是"有支持（房东声明）"，其他材料没提不等于没有。
- 凶宅（5 年内严重暴力犯罪）、水灾山火、制毒、外墙包层整改、已排定大修等是法定必须如实告知的事实：直接问，答复记为"中介声明"，没问过是未知。
- 宠物按 2025-05-19 起的法定流程判断（只能按法定理由拒绝、21 天不答视为同意、strata 一刀切禁宠无效），不按挂牌一句 no pets。
- 垃圾道、包裹房、管理员这类设施没有材料就是未知，不按楼龄楼高猜；硬条件未知就是"待确认"，不算满足。
- 安静程度用噪音源数据（临路等级、机场等高线、酒牌场所）推断；看房时随口的种族、年龄、学生比例之类描述不进入任何评分，也不当替代变量，看房清单里根本没有这些项。

## 4. 首版三件事、交互方式与演示脚本

### 4.1 首版三件事

1. 需求变清单（Nemotron）：一句话需求拆成房间级、时间级、位置级的检查项，标明硬条件还是软偏好、什么材料能回答它；五样必填项为空时先反问（4.3 节）。
2. 逐套核对（Zetaris 跨源查询）：对每套候选房，从挂牌、照片事实、公开数据、中介回复、看房所见取证据，给每个检查项打状态和出处，未知的标明下一步（问中介 / 看房时看 / 签约时核），生成"房源 × 条件"矩阵。
3. 追问和更新（Meterless 状态与记忆）：未知项按"会不会改变选择"排序，生成问中介的问题；粘贴中介回复或传看房照片后，状态更新、排名变化、保留历史。

### 4.2 交互方式：语音导览（演示全英文）

一句话：用户说需求，助手边查边说，房源卡片从左边飞进来，逐套讲"为什么合适、哪里特别、我是怎么确认的"，用户随时插话。决定于 2026-10-25（DECISIONS）。

- 界面由事件驱动。模型不直接画界面，它输出一串小事件：说一句、显示哪张卡、高亮哪一格、拉出哪条证据、哪个来源查完了。前端按顺序演，所以画面和话永远对得上，也能反复录到满意。事件协议见 src/voice/README.md。
- 画面分区：中间是对话与状态（听、分析中、说）；左边房源卡片滑入，每张带四色状态格；右边"来源发现"面板，每行是一次 Zetaris 查询，查完打钩并显示 request_id；底部证据抽屉，写来自哪张表、哪一行、哪次查询。矩阵表保留为"全部结果"视图，也是录制失败时的保底。
- 像真人的四个做法：先开口再查，等待 Zetaris 的 2 到 40 秒变成"我正在查五个来源"；逐句播，流式输出按句切给合成，首字 2 秒内；不胡说，旁白只从证据矩阵生成，每句"为什么合适"对应一个格子和它的证据；声音由超亮亲耳挑，候选 Magpie、ElevenLabs、OpenAI，本机和浏览器自带的声音只用来调试。
- 语言：视频、合成数据、界面、旁白全英文；内部文档中文。

### 4.3 反问规则：需求侧的"未知"也不猜

1. 开查前必须知道五样：周租预算上限（A1）、几房或几个人住（B1）、区域或上班地点（G1）、入住时间（A4）、有没有宠物（J1）。
2. 缺了就问，一口气最多问两样，问完就查；不缺的一个字不问。
3. 其他信息缺了不问，先假设、说出口、随时改。例如 "I'll assume unfurnished is fine, tell me if not."
4. 最多问两轮。之后哪怕还缺，也先给结果，带着假设讲。
5. 问什么由程序判断（清单里的必填项为空），怎么问由 Nemotron 写。和房源侧一个原则：程序算，模型说。

讲法：房源侧有"未知"状态，不编证据；需求侧也有"未知"，不替用户猜预算。两边都不编。

示范：用户 "Two bedrooms near Central, I have a cat." 助手 "Got it. Two quick things before I search: what's your weekly budget, and when do you need to move in?" 用户 "Under 900, mid-November." 助手 "Thanks, searching now."

### 4.4 打断标准（五条）

1. 用户一开口就停，300 毫秒内。
2. 记得说到哪句被打断：旁白按句播，记"已说到第几句"，不重复、不丢。
3. 不被自己的声音打断：浏览器回声消除，播放时提高说话检测门槛，识别结果和正在播的句子高度重合就当回声忽略。
4. 被打断后先回应，再决定怎么接：问的是问题，答完接着讲；改的是需求，重排再讲；说"skip"，下一套；说"stop"，停下等指令。
5. "嗯""对""okay"这种短于半秒、没有实词的声音不算打断。

实现分两步。原型先在浏览器端做（能量检测 + 句级队列 + 回声消除 + 回声文本过滤），不依赖任何 key，今天就能测手感。拿到 NVIDIA key 后换 Pipecat 骨架接 Parakeet 识别和 Magpie 合成（NVIDIA 官方 Nemotron Voice Agent 蓝图就是这条链），前三条由它自带，后两条是我们的对话策略，事件协议不变。

### 4.5 演示脚本（英文，3 到 4 分钟）

1. 用户说："Two bedrooms near Central, I have a cat, and I'd like air con in the bedroom."
2. 助手反问："Got it. Two quick things before I search: what's your weekly budget, and when do you need to move in?" 用户："Under 900, mid-November." 助手："Thanks, searching now."
3. 右侧来源面板逐行亮起：挂牌页、户型图与照片事实、中介回复与 by-laws、租金中位数、通勤表。助手边等边说 "I'm checking five sources, this takes a few seconds."
4. 第一张卡从左滑入。助手逐格讲：预算有支持；两房有支持；养猫推断（by-laws 没禁，中介未确认；下一步：问中介）；卧室空调推断（挂牌 features 写 split system，照片里内机在客厅，卧室没拍到；下一步：问中介）。说到哪格哪格高亮，证据从底部拉出，带表名、行号、request_id；未知的格子旁边标着下一步是问中介、看房时看还是签约时核。
5. "The one question worth asking this agent is about the cat. A yes turns that cell from inferred to supported."
6. 翻第二套，讲特别点（唯一一套中介已经书面回复两间卧室都有出风口）。用户插话 "Is the first one close to the station?" 助手停下，答（通勤表 G1，有支持，18 分钟到 Central），然后 "Back to the second place."
7. 用户说出中介回复 "Split system in the living room only." 第一套的 C1 从推断变冲突，排名变化，变化记录面板出现（Meterless World Model）。
8. 结尾 10 秒：风水偏好包。"My mum cares about feng shui: no 4 in the unit number, and no front door facing the balcony door." 清单多两项；门牌从地址直接读出，穿堂按户型图标"推断"，门窗位置画不清的房源标"未知"。

## 5. 数据

- 字段结构：REA 和 Domain 搜索 filter 的全部字段，加挂牌页的新增字段（含网络 / NBN），加看房时自己能看到的维度（炉灶、空调内机位置、新旧、霉味、噪音、日照）。
- 造法：先生成隐藏真值（这套房到底什么样），再渲染成挂牌文案、照片描述、户型文字、中介回复、看房照片与勾选（模拟租客看过的那些套）。每条打两种标签：真值是什么；现有材料够不够回答。真值是"没霉菌"但材料没提，正确答案仍是"未知"。
- 故意埋坑：缺失、矛盾、过期、Virtual Staging、错房号、只写"有空调"、价格改过。
- 规模：50 套房源、30 套带中介书面回复和看房勾选、3 张公开数据表；重点是花样，不是数量。
- 真实公开数据直接用：租金中位数、通勤时间、建筑高度、持牌场所、地点；完整来源表见第 6 节。
- 合成房源用虚构门牌加真实 suburb（Kensington、Kingsford、Zetland、Haymarket），不给真实地址编合同、缺陷、竞争人数。
- 户型按结构化布局生成（房间轮廓、门、窗、炉灶、厕所门的位置）再渲染成图，门牌和楼层写进地址。这样偏好包的规则能直接核对，也能埋"户型图没标炉灶、门画得不清"这种坑。

维度清单（从一份真实的代看房记录样本和会议提炼）：家具是否随租；空调在哪个房间、冷暖、能否用；厨房开放式与否、炉灶类型、烤箱、油烟机、通风；洗衣房位置、设备是否包含、能否自装；卫生间干湿分离、花洒；阳台大小与视野；客厅大小；临街安静程度与隔音；插座数量；门禁、车位；楼龄、霉菌、维修；到学校的公交步行时间与班次；超市、餐饮距离；总成本（租金、bills、家具）；朝向、窗户位置、前方遮挡、指定季节时段的直射日照。可选偏好包（风水，用户打开才查）：门牌和楼层数字、入户门正对阳台门或大窗、开门见厕、开门见灶、厨厕门相对、户型缺角。

## 6. 数据来源：材料分五段，每格说三件事

一句话：材料按"什么时候能拿到、从谁手里拿到"分五段；矩阵里每一格只说三件事——直接证据是什么、间接证据只能说明什么、还不知道的下一步找谁。在新州，租客申请前拿不到第三方看房报告，所以它不是基础材料；替代它的是租客自己看房时按我们清单拍的照片和勾选。代看房只是可选服务。

### 6.1 五段材料（代码字段 stage；分类名和代码一字不差）

| stage | 中文 | 界面英文 | 包含什么（对应数据表） | 直接证据 | 间接证据只能说明什么 |
|---|---|---|---|---|---|
| listing | 挂牌就有的 | From the listing | 文案、features 勾选、价格、bond、可入住日、照片、户型图（listings、photo_facts、floorplan_facts） | 租金、几房、日期、features 勾选（房产级："有空调"只说明房产里有，不说明哪个房间） | 照片推新旧、炉灶类型、是不是虚拟布置；户型图推朝向和布局 |
| public | 公开可查可算的 | Public data | DCJ / Domain 中位租金、通勤时间、太阳几何日照、临路噪音、洪水山火图层、楼龄（public_rent、public_transit、sun_geometry；洪水山火和楼龄首版没接，如实标未知） | 算出来的算直接证据：租金对比、通勤 | 日照只算天空几何、没算遮挡，是间接 |
| agent | 问中介能拿到的 | From the agent | 中介回复（邮件 / 短信，带时间戳）、strata by-laws（法定签约前必须给，一问通常就给）、法定必须如实回答的披露（5 年内凶案、水灾山火、制毒、松散石棉、外墙整改、待售） | 中介声明是直接证据，分量低于法定表格和合同；by-laws 条款是直接证据 | — |
| viewing | 自己看房看到的 | Your viewing | 租客按我们给的清单在看房时拍的照片和勾选项（炉灶、空调内机位置、噪音、日照、新旧、水压、霉味）。这一项替代原来的"看房报告"；代看房只是可选服务，不是基础材料 | 自己看到的是直接证据 | — |
| signing | 签约时才拿到的 | At signing | 标准租约草案、条件报告（Schedule 2）、inventory、by-laws 正本 | 只做最后核对，不做筛选输入（docs/01 R-D1），永远不是排名的证据来源 | — |

每一格统一说三件事：直接证据是什么 → 间接证据只能说明什么 → 还未知的下一步三选一（代码字段 next.kind）：

- `ask_agent`（Ask the agent）：问中介能答的，例如宠物、法定披露、哪个房间有空调。
- `see_at_viewing`（See at the viewing）：只有自己去看才知道的，例如炉灶、噪音、霉味、新旧。
- `check_at_signing`（Check at signing）：要等合同、条件报告、inventory 才能核的，例如 bills 条款、家具清单。

以前产品只有"问中介"一种下一步，这次补齐三种。未知的硬条件在排名里按"待确认"处理，不算满足，也不算扣分。

### 6.3 来源发现

Agent 不是拿着固定清单硬查。对每个检查项，它先问 Zetaris 的元数据：这个地址、这个维度，有哪些表和字段能回答？然后才查数据。界面上显示"这一项找到了 3 个来源：挂牌 features、中介回复、看房时自己看"。这一步和 Track 1 的题目（分散的信息）直接对应。

### 6.5 评委可能问的五个问题

1. 为什么材料里没有"看房报告"？
   在新州，租客申请前拿不到第三方看房报告：中介不出，网上也查不到。有人愿意花钱请人代看，那是可选服务，不是人人都有的材料。所以基础材料里没有它，替代它的是租客自己看房时按清单拍的照片和勾选。

2. 真有一份详细的看房报告，还要你们干嘛？
   我们的价值在看房之前：从一堆挂牌里筛出值得去看的几套，并把每条判断的证据和"还没确认的要问谁、看什么"摆出来。看房照片和中介回复是后来补进来的输入，不是前提。真有一份报告，它进来就是 viewing 段的证据，结论照样更新。

3. 间接证据能说明什么？
   只能说明"大概率"，说明不了"确定"。照片里台面旧，推断房子旧，但照片是挑最好的时候拍的；features 勾了"有空调"，只说明房产里有一台，不说明卧室有。这类格子一律标"推断"，不算满足硬条件，旁边写明去哪确认。

4. 未知怎么办？
   未知不猜，也不算满足。每个未知格子标一个下一步：问中介能答的（宠物、法定披露）标"问中介"；只有去看才知道的（炉灶、噪音、霉味）标"看房时看"；要等合同和条件报告的（bills 条款、inventory）标"签约时核"。排名里未知的硬条件按"待确认"处理。

5. 条件报告为什么不算筛选输入？
   NSW 规定条件报告在签约前或签约时才给，租客 7 天内回签。筛房的时候根本没有它，拿它做筛选输入等于用不存在的材料。它只在签约那一步做最后核对，而且只记 Y/N，不记几台、好不好用。

## 7. 赞助商集成：具体到接口、表和演示

### Zetaris：所有取证都走它，数据留在原地查询

- 做什么：把 6 类来源挂成一个能用 SQL 查的层：listings、documents（中介回复、by-laws、handbook、看房勾选、合同、条件报告、inventory，都是 JSON 行，每行带 stage）、photo_facts（挂牌照片和租客看房照片的可见事实，source 区分）、public_rent、public_transit、public_built（建筑高度、噪音源、地点）。Agent 的"逐套核对"把每个检查项翻译成一条查询，返回带表名和行号的证据。
- 怎么接：队友建的 Zetaris Cloud 实例（已连通；S3 桶 CSV 的注册和查询 10-25 已跑通，见 infra/zetaris.md）；Postgres 挂为一个数据源，CSV 各挂一个；每个维度建一个视图（例如 v_ac_evidence、v_sun_inputs）；调用走 Lapse 里已验证的 REST 路径 POST /sql-editor/sqls/run，每次查询有 queryId。
- 演示里看到什么：点开矩阵任意一格，显示"证据来自 documents.agent_reply 第 12 行，Zetaris 查询 #184"，并能展开 SQL。来源发现那一步也在这里。
- 留什么证据：Zetaris 查询日志导出；README 里写每个维度对应的视图和一条样例查询。
- 风险与回退：账号和配额未知；CSV 大小限制未知。回退是本地 DuckDB 跑同样的 SQL，但 README 和视频里如实标注"回退"。

### Meterless：记状态、记记忆、记运行

- World Model Engine：每套房每个维度一条"信念"记录，字段是值、状态、来源 material_id、版本、时间。新材料到达只追加新版本，不删旧版本；只重开被翻转的决定（A 房因为空调从"未知"变"不满足"，排名才动）。这套机制从 Lapse 原样搬来，一致性测试已经是绿的。
- H-MEM：用户需求画像、每次决定、问过中介的问题，跨会话保留（"你上次说不要公共洗衣房"）。
- Nightshift：官方要求它是产品运行时的主 provider，NVIDIA 奖也要求 Nemotron 经它跑。所有模型调用经它转发并记录 prompt 哈希、模型名、耗时，评测能复跑。装在 Mac 上，Providers 填 NVIDIA key，Console 给应用 URL 和 token（docs/hackathon/rules.md 的 Power 段）。
- 演示里看到什么："变化记录"面板：A 房 C1.bed1 未知 → 不满足，来源 M-0001-reply-03，时间 10-26 14:02；评委问"为什么"能点开看。
- 留什么证据：引擎调用日志；README 写明哪个 engine 在哪个功能里起作用（规则要求至少一个 engine 参与工作功能）。

### NVIDIA Nemotron：读需求、看材料、下判断、提问题

- 需求解析：一句话变检查项 JSON（维度编号、房间、时段、硬或软）。
- 材料理解：挂牌文案抽取 features 和模糊措辞；照片理解用视觉模型看内机、炉灶表面、staging 水印、家具，租客看房拍的照片走同一个模型；看房勾选项直接入表，不经模型。
- 判断：对每个检查项，给定证据片段，输出状态、引用、冲突说明，受规则表约束，结构化输出。
- 追问：未知项按"会不会改变选择"排序，法定必答项优先。
- 怎么接：产品运行时走 Meterless Nightshift（官方 Power 规则，见 docs/hackathon/rules.md）：应用 → Nightshift Runtime（OpenAI 兼容，METERLESS_BASE_URL + Runtime token，路由 meterless/auto）→ NVIDIA。Nightshift 的 Providers 里填 NVIDIA key；Lane 1 文本 nvidia/nemotron-3.5-lightning-30b-a3b，Lane 2 视觉 nvidia/nemotron-3.5-super-vl-120b-a12b（103 案例里直连调用过）。开发期可直连 integrate.api.nvidia.com/v1 同名模型。旧的 nemotron-3-nano-30b-a3b 已下线。key 还没拿，自检脚本 scripts/check_nvidia.py。
- 演示里看到什么：需求解析卡片和照片事实卡片都标模型名；对照实验的两条路用同一个模型。
- 语音（可选赞助商链）：识别 Parakeet、合成 Magpie，都在 build.nvidia.com，用 Pipecat 骨架接（NVIDIA 官方 Nemotron Voice Agent 蓝图就是 Parakeet → Nemotron → Magpie）。没拿到 key 之前，原型用浏览器自带识别和本机合成顶着；合成声音最终由超亮听过再定（Magpie / ElevenLabs / OpenAI）。
- 对话策略里"问什么"由程序定（五样必填项为空），Nemotron 只负责措辞；"为什么合适"的每句话都从矩阵格子和证据生成，模型不能自由发挥。

### Cursor：开发工具，也是规则的载体

- 规则要求开发用 Cursor。把附录里的判断规则写成 .cursor/rules，让 Cursor 在写判断代码时按规则来。
- 留什么证据：提交记录、截图、README 里一段"Cursor 用在哪"。

## 9. 对照实验

同一个 Nemotron 模型跑两条路：A 只看挂牌文字直接回答；B 走多源核对加状态标注。在 20 条需求 × 50 套房的合成集上比三项：硬条件误判率（把"未知"当"满足"）、正确说"未知"的比例、追问是否命中会翻转结论的未知项。数据有隐藏真值，自动评分，半天能跑完。
